# Agent 面试问答：基础概念、工程设计与安全

整理依据：[我的 Chapter 0：入门概念](../books/ai-agent-book/Chapter0.md)、《AI Agent 从原理到实践》[第 1 章：AI Agent 入门][book]及其[思考题][exercises]。原书内容读取于 **2026-09-17**。

本页共 24 题：先给适合口述的结论，再补充面试可能追问的条件、例子和取舍。原书思考题没有标准答案，以下均为参考作答；幂等、状态校验、指标设计等细节属于结合原理给出的工程补充，不是原书的逐字答案。

## 一、核心概念与运行机制

### 1. 什么是 Agent？它与普通的 LLM 问答有什么区别？

在本章讨论的 **LLM Agent** 范围内，Agent 是一个围绕目标，根据环境反馈持续选择行动的系统。LLM 负责决策，上下文提供决策所需的信息，工具提供读取或改变环境的接口。

可以用 `Agent = LLM + 上下文 + 工具` 概括最小工程组成，但不能只看有没有这三个组件，还要看它们是否形成了**行动—反馈—再决策的闭环**。

- 普通问答通常完成一次输入到输出的转换。
- Agent 可以搜索资料、读取结果、发现信息不足、换一种搜索方式，再综合答案。
- 调用一次工具可以是 Agent 的一个步骤，但“接了工具”本身不足以说明系统具有多少自主性。

**面试补充：**这是现代 LLM Agent 的工程描述，不是所有控制论或强化学习 Agent 的统一定义；环境也不是公式里的内部组件。

依据：[原书：最小组成][components]。

### 2. Harness 是什么？它和 Model、Environment 的边界在哪里？

Harness 是 **Agent 内部、模型之外的运行与治理层**：把模型的决策接到真实工具上，并控制权限、状态、验证和恢复。`Agent = Model + Harness` 是对上一题同一套系统的另一种划分。

| 职责 | 解决的问题 | 退款 Agent 示例 |
| --- | --- | --- |
| 上下文管理 | 当前需要知道什么 | 提供订单状态、退款政策、已完成步骤 |
| 工具接口 | 如何读取或执行 | 查询订单、提交退款、查询退款结果 |
| 约束 Constrain | 哪些操作允许发生 | 校验身份、金额上限、订单归属 |
| 验证 Verify | 结果是否符合目标 | 核对退款记录、金额和订单状态 |
| 纠正 Correct | 失败后如何处理 | 查询不确定结果、有限重试、补偿或转人工 |

**边界要说清：**工具定义、适配器、沙盒权限属于 Harness；数据库里的订单、沙盒中的文件和进程状态属于 Environment。即使它们部署在同一台机器，也不能把环境整体算进 Harness。

依据：[原书：Harness 工程][harness]。

### 3. ReAct 循环如何运行？模型会直接执行工具吗？

ReAct 将推理与行动交替组织起来：**根据已有信息决策 → 请求工具调用 → 运行时执行 → 接收观察 → 再次决策**。

一个完整的调用链包括：

1. 运行时给模型提供目标、历史和工具定义。
2. 模型返回工具名称、参数和调用标识。
3. 运行时校验参数、权限和预算，然后执行工具。
4. 把结果或错误与对应调用关联，加入后续上下文。
5. 模型继续行动，或提出最终回答；系统按完成标准确认结果。

**关键区分：**模型产生的是调用决策。真正读取文件、访问数据库或运行代码的是外部运行时。使用服务端托管工具，只是把这部分循环交给了服务提供方。

不必要求每个模型都公开内部思维链。可观测性主要依靠任务状态、工具调用、结果、验证记录和必要的决策摘要。

依据：[原书：ReAct 循环][react]。

### 4. 工具返回成功、模型停止调用工具，是否意味着任务完成？

不一定。需要区分 **调用成功、业务成功、任务完成**。

例如退款接口返回 HTTP 200，可能只是成功受理；退款最终到账还需要查询业务状态。而即使退款已完成，如果退错订单或金额，也没有满足用户目标。

可以分三层检查：

- **调用层：**调用是否执行、返回值能否解析、是否存在超时或部分失败。
- **业务层：**实际资源状态是否满足业务约束，例如订单、金额、收款方是否正确。
- **目标层：**用户要求的所有事项是否完成，是否还有未解决的问题。

模型不再请求工具，只能作为结束执行的信号之一。高影响任务应使用受信任的业务状态、测试或其他独立证据验证，不能仅凭模型说“完成了”。耗尽预算也应标记为未完成，而不是成功。

依据：[原书：上下文消融实验][context]、[Harness 的验证与纠正][harness]；分层检查为工程补充。

## 二、模型选型与编排选择

### 5. 如何为一个 Agent 选择模型？是否一定要用推理模型？

先确定任务和约束，再用真实任务评估候选模型。复杂规划和长链工具调用可以优先评估推理模型；简单分类、抽取或单步定位，较轻的模型可能更合适。**最终依据是任务效果与成本，而不是模型类别的名字。**

| 维度 | 重点检查 |
| --- | --- |
| 任务能力 | 成功率、工具选择、参数正确性、失败恢复、长任务稳定性 |
| 接口与策略 | 是否提供所需工具和输入模态，是否允许目标用途 |
| 延迟 | 首次响应、完整任务耗时、P95 延迟、工具等待时间 |
| 成本 | 输入输出与缓存费用、调用轮数、重试和工具费用 |
| 部署条件 | 数据要求、可用性、限流、维护能力、服务条款 |

开源或开放权重模型便于定制和控制部署，但不自动意味着总成本更低，还要计算推理资源与运维成本。

**容易被追问：**Grounding 是把指令对应到屏幕元素、坐标或其他对象的能力，与 Reasoning 不是互斥分类。多步 Computer Use 往往同时需要视觉定位、规划和结果验证。

依据：[原书：如何选择模型][models]；这里将书中的选型建议写成了需要实测的条件判断。

### 6. 只能升级模型、上下文或工具中的一项，你选哪一个？

**对应原书思考题 1。**

我会先找失败瓶颈，再决定投资方向。缺信息、缺行动能力和决策能力不足，是三类不同问题。

- **缺信息：**例如不知道企业最新退款政策，优先补检索、状态和上下文组织。
- **缺接口：**例如知道要退款，却没有退款工具，优先补工具。
- **决策不稳：**信息和工具已足够，仍反复错误规划或传错参数，再评估更强的模型。

如果必须在没有更多信息时选一个，我会先检查任务所需信息是否可见，因为不少失败来自上下文缺失；但这只是待验证的假设，不是“上下文永远最重要”。

验证时固定另外两项，分别做对照实验，比较任务成功率、成本和风险。更多文档可能增加噪声，更多工具可能增加误选，因此升级应针对缺口，而不是单纯增加数量。

依据：[原书：观察与动作接口][interfaces]、[思考题][exercises]。

### 7. 单次 LLM 调用、工作流、自主 Agent，应该怎么选？

按解决问题所需的最小复杂度选择：**单次调用能解决就先用单次调用；步骤和规则明确时用工作流；路径需要随反馈变化时再引入自主 Agent。**

| 方案 | 适用情况 | 例子 |
| --- | --- | --- |
| 单次调用 | 信息齐全，输出可一次生成或判断 | 分类、摘要、字段抽取 |
| 工作流 | 步骤、状态转换和异常分支可预先定义 | 审批、订单处理、固定资料审核 |
| 自主 Agent | 下一步取决于探索中获得的信息 | 调研、故障排查、开放式代码修复 |

工作流也可以有条件分支、循环和人工节点，不等于所有请求都走同一条直线。主要区别是：允许的控制路径由程序定义，还是较多地交给模型在运行时决定。

复杂架构应由明确业务约束或反复出现的失败来推动。多一个 Agent 或节点，就多一份状态、通信成本和故障来源。

依据：[原书：编排模式][orchestration]。

### 8. 航班订票客服应该用工作流还是自主 Agent？如何混合？

**对应原书思考题 6。**

我会让 Agent 负责需求澄清、航班比较和异常解释，让确定性的业务流程负责身份、价格确认、支付、出票及补偿。

一个可行的划分是：

1. **灵活决策部分：**理解目的地、日期、预算、行李和转机偏好；根据查询结果调整候选方案。
2. **业务校验部分：**校验旅客信息、实时价格、库存、退改规则和用户授权。
3. **交易执行部分：**按供应商实际协议管理锁座、支付和出票的状态转换；不能假设所有系统都必须“先付款后预订”。
4. **异常处理部分：**支付结果不明时先查询；失败时按规则释放资源或补偿，必要时转人工。

模型不能通过自然语言直接跳过交易约束。金额、旅客或航班发生变化后，应重新校验原授权是否仍然适用。

**取舍：**灵活性放在方案探索里，确定性放在交易边界上；不必为了表达这种分工就创建多个 Agent。

依据：[原书：工作流与自主模式混合][hybrid]；交易状态与恢复细节为工程补充。

## 三、工具、上下文与运行效率

### 9. 什么是 ACI？怎样设计模型不容易误用的工具？

ACI 是 Agent-Computer Interface，强调从 Agent 的使用角度设计接口：让模型容易判断**何时调用、如何传参、会产生什么影响、失败后怎么办**。

我会重点做好：

- **名称和职责清楚：**例如 `get_order` 与 `refund_order` 分开，避免含义模糊的 `process`。
- **参数有明确语义：**金额单位、时区、资源 ID、允许值、边界和例子写清楚。
- **危险操作受限：**权限范围由服务端绑定，模型不能靠传入一个用户 ID 就获得该用户权限。
- **结果可用于决策：**返回状态、实际影响对象、错误码、是否可重试及下一步查询方式。
- **副作用可控：**写操作考虑幂等、预览和执行结果查询，避免因重试重复扣款。

通用代码工具适合探索和组合；支付、删除等强业务操作通常更适合专用接口。参数格式正确，只说明请求能被理解，不代表调用被授权或业务上正确。

依据：[原书：工具][tools]、[构建有效 Agent 的原则][principles]。

### 10. 受限动作空间在什么场景下优于开放动作空间？

**对应原书思考题 8。**

当任务范围明确、错误代价高、审计要求强时，受限动作空间通常更合适。例如退款客服只能查询订单、计算可退金额、申请退款和转人工，而不提供任意 SQL 或任意命令执行。

它的优势是容易校验、测试和审计，也能缩小误操作的影响范围；代价是灵活性下降，遇到未覆盖情况需要扩展接口或转人工。

开放动作空间更适合代码开发、探索性分析等难以穷举步骤的任务，但必须配合隔离和权限控制。

**追问重点：**开放与受限是程度差异。即使动作名称有限，某个工具允许传任意代码，也可能具备很大的实际权限；反过来，自主 Agent 也完全可以只使用一组受限的业务工具。

依据：[原书：观察与动作接口][interfaces]、[思考题][exercises]。

### 11. Agent 的上下文包含什么？是否越长越好？

上下文是模型当前决策能看到的信息。基础消息循环里通常包括：系统指令、工具定义、用户消息、模型历史输出、工具执行结果。检索到的知识、任务状态和用户记忆，需要被加载后才会参与当前决策。

上下文不是越长越好，重点是**相关、可信、足够且能反映当前状态**。

- 稳定规则和常用定义可以放在稳定前缀中。
- 按需检索知识或加载工具细节，避免把所有文档和工具一次塞入。
- 保留当前目标、关键约束、已完成步骤、失败原因和证据位置。
- 对大段结果使用摘要、分页和外部文件，但保留可回查的原始证据。
- 标明外部信息来源，避免把网页里的文字当成高优先级指令。

**追问重点：**没有进入上下文的长期记忆，当前模型调用未必知道；模型参数中的知识也不是可随时编辑的业务数据库。书中的“静态前缀 + 轨迹”是基础模式，实际系统可以动态加载和压缩。

依据：[原书：上下文][context]、[渐进式披露][patterns]。

### 12. 为什么 ReAct 累计缓存读取量会近似二次增长？怎么降低？

**对应原书思考题 2。**

因为每轮虽然只新增一小段信息，后续请求却会反复带上此前的历史。**缓存命中可以减少重复计算或费用，但不等于旧历史从后续请求中消失。**

设初始前缀长度为 `P`，每轮平均新增历史为 `d`，运行 `n` 轮。若不压缩，第 `t` 轮输入量约为：

```text
L(t) ≈ P + (t - 1) × d
累计输入量 ≈ n × P + d × n × (n - 1) / 2
```

当稳定前缀持续命中缓存时，累计缓存读取 token 也可能呈同量级增长；准确数值还取决于首次未命中、缓存粒度和服务计量方式。这里估算的是累计 token 量，**不等于断言显存占用或实际延迟一定按平方增长**。

降低增长可以从三个方向入手：

1. **减少轮数 `n`：**改善工具接口，一次返回足够的信息；批量处理或并行执行相互独立的调用。
2. **减少每轮增量 `d`：**限制日志、表格和网页回传量，只保留决策相关字段，大结果存文件后按需读取。
3. **控制活跃历史长度：**做阶段性摘要、滑动窗口或任务分段，保留目标、关键证据和未完成事项。如果每轮输入被限制在固定预算 `B` 内，累计输入可控制在约 `O(nB)`；摘要本身也有开销。

**容易答偏：**稳定前缀提高缓存复用率，但单靠只增不改不能消除历史增长；上下文截断会丢信息，需要验证后续任务成功率，而不是只看 token 降了多少。

依据：[原书：ReAct][react]、[只增不改][patterns]、[思考题][exercises]；公式与复杂度解释为推导。

### 13. Agent 为什么会陷入循环？怎样检测和终止？

**对应原书思考题 4。**

除了工具结果缺失，循环还可能来自：重复遇到同一种错误、读到了过期状态、上下文丢失了已有尝试、目标不明确、工具不可用，或者模型持续使用无效策略。

我会组合使用三类信号：

- **重复信号：**相同工具与规范化参数反复出现，且环境状态没有变化。
- **无进展信号：**连续多轮未产生新的有效证据，未推进任务状态，验证仍因同一原因失败。
- **预算信号：**总轮数、墙钟时间、token、费用或失败次数超过上限。

恢复动作依次可以是：修正参数、补充缺失信息、对临时故障做有限退避重试、改用其他授权路径；持续无进展则停止并保存现场，明确说明未完成原因。

**关键例外：**分页、异步状态轮询可能合法重复，不能只数调用次数。写操作超时也不能直接当作没执行，应先查询状态或使用幂等键，防止重试产生重复副作用。

依据：[原书：自主 Agent 的停止条件][autonomous]、[思考题][exercises]；检测策略为工程补充。

## 四、护栏、权限与人工接管

### 14. Agent 护栏分哪三层？为什么只靠提示词不够？

护栏可以按上下文层、执行层和数据层组织。越接近实际权限和数据状态的强制检查，越不依赖模型是否正确理解了提示词。

| 层次 | 管什么 | 示例 |
| --- | --- | --- |
| 上下文层 | 模型接收什么信息、如何区分来源 | 来源标注、内容检测、输入限制、指令与数据分离 |
| 执行层 | 哪些动作允许执行或输出 | 参数与权限检查、沙盒、审批、输出隐私检查 |
| 数据层 | 哪些数据最终允许被读取或改变 | 行级权限、约束、受控视图、受信任的身份绑定 |

例如恶意网页诱导客服“导出所有客户订单”，即使模型信了这句话，工具凭证和数据库权限仍应把读取范围限制在已授权的数据内。

提示词属于模型需要解释的信息，不能替代强制权限边界。多层防护也不是天然安全，仍要检查是否共用了过宽凭证、是否存在绕过路径。

**面试提醒：**JSON 合法不代表可信；结构化字段也可能来自攻击者。关键是可信身份、授权和实际操作的校验，而不是仅检查数据格式。

依据：[原书：护栏与安全性][guardrails]。

### 15. 上下文护栏有哪些？如何兼顾安全与误拒绝？

常见机制包括相关性分类、安全分类、内容审核、长度等确定性限制，以及来源标注。它们承担不同目标，例如偏离主题不等于有害，业务是否需要拦截应分别决定。

两个概念要区分：

- **越狱：**试图让模型突破其安全策略。
- **提示注入：**把不受信任的内容当成指令，改变系统原本要完成的任务；间接注入常藏在网页、文档或工具结果里。两者可能重叠。

书中的规则驱动分类、上下文联合判断、轻量探针加复审，是一种分类器系统的设计思路。其中“读取模型内部激活”的探针需要相应模型访问与部署条件，普通应用调用黑盒 API 时不能默认具备，也不能一概称为零成本。

评估要同时覆盖危险请求的漏放、正常请求的误拒绝，以及新增延迟和成本。可以让不确定样本进入复核，而不是把第一层告警全部直接当作拒绝。

**工程补充：**SQL 安全不能依赖关键词或正则过滤，应使用参数化查询、受限接口和权限控制；固定工作流也可能传递受污染的参数，仍需校验。

依据：[原书：护栏类型][guardrail-types]。

### 16. 同一个工具随参数不同，风险不同，如何动态评估？

**对应原书思考题 7。**

风险评级应针对**这一次具体操作**，而不只是工具名称。可以把工具基础风险、有效参数、资源敏感度、调用者权限、影响范围和可逆性作为策略输入。

以 `delete_file(path)` 为例：

1. 明确真实目标：规范化路径，处理符号链接与路径越界，识别目标是否属于授权工作目录。
2. 明确影响范围：单个临时文件、整个目录、生产配置文件，风险显然不同。
3. 校验权限和可恢复性：是否有对应授权、能否放入回收区、是否有备份。
4. 根据策略允许、要求具体确认或拒绝；系统禁止的操作不能仅靠模型打低风险分来放行。
5. 执行时再次核验目标与授权，避免审批后路径、内容或资源状态变化。

审批应绑定具体资源、参数和范围。不能批准“删一个普通文件”，实际执行时却换成另一个目录。

**实现取舍：**模型可以辅助解释语义风险，权限和资源范围应由可测试的策略代码强制执行。

依据：[原书：工具风险评级][guardrail-types]、[思考题][exercises]；动态策略细节为工程补充。

### 17. 需要人工确认，但用户不在线、回复慢或含糊，怎么办？

**对应原书思考题 9。**

把任务转入明确的“等待确认”状态，保存已完成步骤、待执行动作和所需决策。**等待超时不等于获得授权。**

- 对需要确认的高影响动作暂停执行，设置合理的超时和取消策略。
- 对已经授权、可独立进行的低风险工作，可以继续收集信息或生成待审方案。
- 给用户具体问题，例如确认哪一个航班、总金额多少，而不是只问“是否继续”。
- 对含糊回复继续澄清；不把“随便吧”无限扩大为任何操作的许可。
- 恢复任务时重新检查价格、库存、资源状态和授权有效性，防止使用过期确认。

对于预先约定的自动处理规则，可以在约定范围内执行；没有这类规则时，到期后应取消、保持待处理或按业务流程转人工队列，并报告状态。

依据：[原书：人工干预][human]、[思考题][exercises]；等待状态设计为工程补充。

## 五、模型进步、系统进化与设计模式

### 18. “模型即 Agent”为什么没有让 Harness 失去价值？

**对应原书思考题 3。**

模型可以越来越擅长决定下一步做什么，但真实工具执行、业务权限、持久状态和结果验证仍由系统提供。**决策能力内化，不等于执行基础设施和业务责任消失。**

随着模型进步，某些繁琐的提示与固定规划步骤可以简化；同时，模型能执行更长、更复杂的任务，也会扩大出错后的影响范围。

因此框架的价值会更多体现为：

- 接入工具并保证权限边界。
- 维护状态、预算、断点和跨会话恢复。
- 管理上下文、证据和数据来源。
- 验证结果、处理异常、提供审计与人工接管。
- 用评估决定哪些机制仍然必要，哪些适配代码可以删除。

不应把“模型更强”推导为“框架一定更复杂”。合理目标是减少多余编排，把不可省略的边界和恢复机制做好。

依据：[原书：模型即 Agent][model-agent]、[思考题][exercises]。

### 19. 哪些 Harness 手段可能过时？哪些原则值得长期保留？

**对应原书思考题 10，也对应 Chapter 0 中“哪些 Harness 被模型内化”的问题。**

容易被替代的是针对具体模型短板的适配代码；值得保留的是验证效果、控制权限、可观测和可恢复等原则。

| 可能简化的手段 | 为什么可能简化 | 仍需保留什么 |
| --- | --- | --- |
| 大量固定 few-shot、显式分步提示 | 新模型可能已较稳定地理解这类任务 | 对新领域仍应实测，示例并非整体过时 |
| 层层提示改写和固定规划链 | 模型可能原生完成理解与规划 | 明确目标、业务约束和结果检查 |
| 针对格式错误的大量字符串修补 | 结构化输出、原生工具接口等降低格式失败 | 语义、范围、权限与业务规则校验 |
| 专门把自然语言改写成生图标签 | 新工具可能直接理解自然语言 | 对用户意图和实际产物的验证 |

**重要区分：**能力改善可能来自模型训练，也可能来自约束解码、API 或运行时支持，不能全部归因于“写进模型参数”。格式可靠也不代表内容一定正确。

删除旧机制之前，应比较有无该机制的任务效果、成本和回归情况，并保留回滚能力。

依据：[原书：工作流适配层][workflow]、[思考题][exercises]。

### 20. Agent 在执行中“学会了”，是否意味着模型参数更新了？

不一定。要先判断变化发生在哪一层。

| 路径 | 改变了什么 | 例子 | 是否更新模型参数 |
| --- | --- | --- | --- |
| 上下文适应 | 当前调用可见的信息 | 看到报错后换参数、根据示例调整格式 | 否 |
| 外部产物更新 | 跨任务可保存的知识或程序 | 更新用户记忆、规则、Skill、工具代码 | 否 |
| 参数更新 | 模型权重 | 监督微调、强化学习等后训练 | 是 |

例如 Agent 第一次查到新的退款政策，当前能按新政策回答，可能只是上下文适应；把政策保存并在下次检索使用，是外部产物更新；这两者都不能直接称为在线训练了模型。

选择哪种路径取决于更新速度、可表达性、验证成本和部署条件。变化快的业务规则适合先放在可审计的外部系统里；并非每个记忆需求都值得微调。

依据：[原书：Agent 的学习机制][learning]。

### 21. 本章的五种设计模式分别解决什么问题？

它们共同追求的是减少盲区、控制信息规模，并让改动可验证、可恢复。

| 模式 | 解决的问题 | 使用时的边界 |
| --- | --- | --- |
| 提议者—审核者 | 产出方可能延续自己的错误判断 | 审核者要有独立标准、必要需求和实际产物；不用照搬产出方的推理上下文 |
| 渐进式披露 | 全量信息挤占上下文，干扰选择 | 目录和索引必须足够清楚，否则需要的信息可能一直没被发现 |
| 只增不改 | 历史难追踪，修改前缀破坏缓存 | 追加式事件记录不等于把无限历史都送给模型 |
| 边界集 + 保留集 | 修好了目标问题，却破坏原有能力 | 同时检查应改变的行为和应保持的行为，并保留独立评估样本 |
| 最小 diff + 可回滚 | 大改动难归因，失败难恢复 | 保留来源和版本；外部副作用可能需要补偿，不能靠代码回滚撤销 |

**追问：审核者也是模型，会不会一起错？**会。独立上下文只能减少部分相关错误；如果模型相同、证据相同或标准错误，仍可能共同失败。关键业务还需要程序校验、测试或受信任状态验证。

依据：[原书：贯穿全书的设计模式][patterns]。

### 22. 如何证明一次 Agent 改动确实变好了？

先定义成功标准和失败类型，再用代表性任务比较改动前后的表现。不能只看回答是否更流畅，也不能只展示一个成功案例。

至少关注：

- **效果：**任务是否真正完成，结果是否正确，是否保留所需证据。
- **效率：**完整任务耗时、token 和工具成本、调用及重试次数。
- **可靠性：**异常恢复率、循环或超时比例、需要人工接管的比例。
- **安全与可用性：**越权或危险请求的漏放，以及合法任务的误拒绝。

针对目标失败建立“边界集”，同时用“保留集”检查原来做对的任务。用于反复调参的样本之外，还应保留独立测试样本，避免把记住题目当成提升。

对随机性较强的任务，可在相同环境快照、权限和预算下重复运行，报告成功率及波动。一次尽量只改一个主要因素，方便定位收益来自模型、上下文还是工具。

依据：[原书：消融实验][context]、[边界集与保留集][patterns]；具体评估流程为工程补充。

### 23. Prompt、Context、Harness、Loop、Graph Engineering 有什么区别？

可以把它们理解为不同范围的工程关注点，而不是必须依次升级的技术等级。

| 视角 | 关注的问题 |
| --- | --- |
| Prompt Engineering | 如何表达指令、要求和示例 |
| Context Engineering | 当前需要哪些信息，如何检索、组织和压缩 |
| Harness Engineering | 如何连接模型、工具、权限、状态、验证和恢复 |
| Loop Engineering | 如何持续推进任务，判断进展、完成或停止，并接续后续执行 |
| Graph Engineering | 如何把 Agent 循环、程序和人工节点组织成有依赖、路由与状态的执行图 |

书中用它们说明工程关注范围的扩展。实践中这些术语的用法并未完全统一，图编排也早于 Graph Engineering 这个名称。简单循环就足够时，不必为了架构名词引入图。

依据：[原书：工程范式的演进][engineering]。

### 24. 用感知、行动、策略三个维度分析一个 AI 产品，并提出改进。

**对应原书思考题 5。以下以 IDE 编程助手为例，面试时可替换成自己实际使用的产品。**

| 维度 | 分析 |
| --- | --- |
| 感知 | 用户需求、读取到的代码、项目规范、诊断信息、命令输出和测试结果 |
| 行动 | 搜索、读取和编辑文件、运行命令、执行测试；提交或发布取决于授权能力 |
| 策略 | 理解目标 → 定位代码 → 做小范围修改 → 验证 → 根据失败反馈调整 |

这种架构适合代码任务，因为修复路径通常无法事先完全确定，需要根据代码和执行结果逐步探索。但“拥有仓库访问权限”不等于“已经读懂整个仓库”，上下文选择仍是关键。

我会优先改进四点：

1. 先获取相关规范、调用关系和测试入口，减少盲目修改。
2. 用最小 diff 保留用户原有改动，记录修改依据。
3. 以测试、构建和验收条件验证效果，避免仅凭模型自评。
4. 将凭证访问、生产操作等与普通本地编辑分开授权，并设置执行预算和恢复点。

是否需要多 Agent，要看是否存在可独立完成、结果可验证的子任务，而不是默认把需求、编码、测试各拆成一个角色。

依据：[原书：Agent 产品的感知、行动与策略][interfaces]、[设计原则][principles]、[思考题][exercises]。

## 七、对 Chapter 0 的修改建议

以下仅记录建议，未改动原笔记。

1. **在两套 Agent 公式后补充 Environment 边界。**建议加一句：“两套公式描述同一个 Agent 的不同抽象层次；Harness 管理模型与环境的交互，不包含外部环境本身。”能避免把数据库、文件等都笼统算作 Harness。

2. **为极简伪代码补充生产条件。**你已注明它是伪代码；作为概念骨架可以保留，但建议补一句：“真实实现还需保存目标和工具调用记录，限制轮数、时间与费用，处理异常，并独立验证完成状态。”尤其不要把 `len(actions) == 0` 直接解释为任务成功。

3. **调整模型选型的分类方式。**“普通对话、Reasoning、Grounding、VLM”不完全是同一维度，也不互斥。可分别讨论推理能力、输入输出模态、定位能力和部署方式；把“大部分需要 Reasoning”表述为“复杂多步任务优先评估推理模型，以实际任务结果为准”。

4. **把性能从输出速度扩展到完整任务。**除了 token/s，补充首响应时间、工具耗时、轮数、重试、P95 延迟和每个成功任务的总成本。输出更快但多错几轮的模型，未必更省时。

5. **限定“两级筛查探针”的适用条件。**读取内部激活是特定分类器实现所需的能力，普通 API 使用者通常无法直接实现。建议写成“具备模型内部访问条件时可使用轻量探针，否则采用可用的规则或分类器做分级筛查”。

6. **补充护栏的强制执行方式。**正则和关键词过滤不能替代参数化查询；数据层也不只是“有没有写权限”，还包括数据归属、行级访问、约束与受信任身份。结构化输出同样不能替代授权与语义校验。

7. **给“模型内化 Harness”的表格加一列“仍需保留”。**Few-shot 不会整体失效；JSON 格式改善可能依赖解码与平台机制；原生多模态能力也不保证结果符合需求。避免把“减少适配代码”写成“可以删除验证和边界”。

8. **为设计模式补充使用边界。**“不共享上下文”不是不给审核者需求和证据，而是避免直接继承产出方的推理偏见与受污染历史；“只增不改”也不代表无限堆积活跃上下文。可分别补上独立验收标准、外部事件记录与上下文压缩。

9. **补全 Graph Engineering 和占位链接。**第 23 题可作为 Graph 的简短释义；“详细评测方式”处的空链接可以先指向本页面的评估部分。文末“思考题”可以链接到本页面，不必重复维护两套答案。“跃近史”建议改为“演进”或“演进史”。
