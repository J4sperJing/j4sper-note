# Agent 面试问答

这是一份通用的面试回答范例。每题先回答问题，再视追问展开；读者可以结合自己的理解和经历调整表达。

> **使用说明：**“项目补充”是备考提示，不需要照读；`【……】` 留给真实经历和数据。做过的内容可以说“我当时做了”，尚未落地的内容保持“如果由我设计，我会……”。文末有一张项目素材卡，可以填好后用于多道题。

## 一、核心概念与运行机制

### 1. 什么是 Agent？它与普通的 LLM 问答有什么区别？

我理解的 LLM Agent，是一个能围绕目标，结合执行反馈决定下一步行动的系统。模型负责判断，上下文提供信息，工具负责读取数据或执行操作，这几个部分通过一个循环配合起来。

比如用户想了解一个线上故障，普通问答可能根据提供的日志给出分析；Agent 则可以继续查日志、核对配置、验证一个假设，再根据结果调整排查方向。它的执行路径不一定在开始时就能确定。

所以我判断一个系统是否具备 Agent 特征，会重点看两点：它有多少决策空间，以及它能否根据环境反馈继续推进任务。只接一个工具，还不足以说明它具备很强的自主性。

**追问：Agent 一定要用 LLM 吗？**

更广义的 Agent 不一定用 LLM，强化学习和控制系统里也有 Agent。这里我说的是当前常见的 LLM Agent 架构。

> **项目补充｜体现“根据反馈调整下一步”**
> 这里适合讲【故障排查／资料调研／代码修复项目】中的一个具体任务：目标是什么，第一次操作获得了什么信息，这个信息怎样改变了后续步骤。选能说明动态决策的片段，比只列“接了搜索、数据库、文件工具”更有说服力。

### 2. Harness 是什么？它和 Model、Environment 的边界在哪里？

Harness 可以理解为让模型稳定运行、连接业务系统的一组代码和机制。模型决定要做什么，Harness 负责把这个决定转成可执行、可检查、可恢复的操作。

我通常从五个方面理解它：给模型组织上下文，提供工具接口，限制操作权限，检查执行结果，以及处理失败后的恢复。

举个退款的例子：模型可以判断需要查询订单或发起退款；Harness 要提供对应接口，检查订单归属和退款金额，记录执行状态，并在超时后查询结果或转人工。订单本身和支付系统的实际状态属于环境。

所以，Harness 的范围是 Agent 内部的运行与治理机制。外部数据库、网页和文件状态，仍然属于它交互的环境，即使这些东西部署在同一台机器上也是如此。

> **项目补充｜区分自己的工程贡献**
> 可以接：“在【项目名】里，我负责的是【工具接入／权限／任务状态／失败恢复】。当时模型已经能完成【决策】，但实际运行还会遇到【具体问题】，所以我补了【机制】。”这里要说清亲自负责的部分，以及为什么需要这层机制。

### 3. ReAct 循环如何运行？模型会直接执行工具吗？

ReAct 的过程可以概括成：根据当前信息做判断，调用工具获取信息或执行操作，再结合工具结果决定下一步。

实现时，程序先把目标、历史和工具定义交给模型。模型返回要调用的工具和参数，运行时完成权限与参数检查，执行后把结果放回上下文。模型可能继续调用工具，也可能给出最终回答。

这里有一个重要边界：模型生成的是调用请求，真正访问数据库、读取文件或运行代码的是外部运行时。使用平台的托管工具，只是把这部分执行逻辑交给了平台。

**追问：怎么观察它的执行过程？**

我会记录每一步的工具、参数、耗时、返回状态，以及任务状态的变化，把请求和结果关联起来。这样可以定位错误发生在哪一步，不需要依赖模型公开完整的内部思维链。

> **项目补充｜拿一条实际调用链说明**
> 准备【某次任务】的三到五个关键步骤：调用了什么、返回了什么、下一步为什么改变。如果确实做过日志或 Trace，也可以说明如何通过调用标识定位一次失败。

### 4. 工具返回成功、模型停止调用工具，是否意味着任务完成？

我会分开看调用有没有成功、业务状态有没有达到要求，以及用户的整个目标有没有完成。

比如退款接口返回成功，可能只是受理了申请，实际退款还在处理中。即使业务状态显示已退款，也要确认订单和金额正确，才能判断用户要求的退款是否完成。

因此我会在任务开始时定义验收条件，再用业务查询、测试或其他可核对的结果来验证。模型不再调用工具可以触发结束检查，但不能直接作为成功依据。

如果只是耗尽时间或调用预算，就应该明确返回哪些步骤完成了、哪些没有完成，不能把停止执行当成任务成功。

> **项目补充｜结合异步业务或验收经历**
> 这里可以讲【支付／消息投递／异步任务／部署】中的真实情况：接口受理成功后，怎样确认最终完成；超时但结果不明时，又怎样查证。即使这段经历来自传统后端系统，也可以说明这类验证机制如何用于 Agent 工具执行。

## 二、模型选型与编排选择

### 5. 如何为一个 Agent 选择模型？是否一定要用推理模型？

我会先明确任务需要什么能力，再用一组接近实际业务的任务比较候选模型。重点看任务成功率、工具调用是否稳定、完整任务的耗时和成本，以及部署和数据要求能不能满足。

如果任务需要多步规划、反复验证，我会优先评估推理模型。对于简单分类、字段抽取或单步定位，较轻的模型也可能足够。是否需要更强的推理能力，还是要看它带来的收益能不能覆盖额外延迟和成本。

性能上我会看整个任务，包含模型生成、工具等待、重试和总调用轮数。一个输出快但经常选错工具的模型，最终可能更慢、更贵。

另外还要验证接口是否支持所需模态和工具，用途是否符合服务要求。自部署模型也要把算力和运维成本算进去。

**追问：Grounding 和 Reasoning 是二选一吗？**

这两个能力可以同时存在。Grounding 负责把指令对应到界面元素等具体对象；Reasoning 更侧重规划和判断。复杂的电脑操作任务，通常既需要正确定位，也需要判断操作顺序和执行结果。

> **项目补充｜模型评估过程**
> 这里可以讲【项目名】比较过哪些候选方案、用了多少条什么类型的任务，以及最终选择的原因。待补：评估集【】；成功标准【】；任务成功率【】；P95 耗时【】；任务成本【】。没有实测的数据先留空。

### 6. 只能升级模型、上下文或工具中的一项，你选哪一个？

如果现有模型已经具备基本的决策和工具调用能力，业务接口也齐全，我会优先检查和改善上下文。因为模型即使有能力，也很难在缺少关键政策或最新状态时做出正确判断。

不过这个选择要随失败原因调整。比如系统知道需要退款，却没有退款接口，应该先补工具；如果信息完整、工具也可用，模型仍然反复做错规划，再考虑升级模型。

实际判断时，我会抽样看失败轨迹，把问题分成缺信息、缺操作能力和决策错误，再固定其他条件做对照。这样能知道投入解决了哪个问题，也能避免增加了一堆文档或工具，却让模型更难选择。

> **项目补充｜讲一次定位瓶颈的过程**
> 可以接：“【项目名】最初出现【失败表现】，我们一开始怀疑【原因】，但检查【日志／样本】后发现实际缺的是【信息或能力】。调整【具体措施】后，在【评估范围】内观察到【结果】。”重点是判断依据，不一定要有很大的提升幅度。

### 7. 单次 LLM 调用、工作流、自主 Agent，应该怎么选？

我会先用最简单、能够满足要求的方案。输入和目标明确，一次调用就能完成的分类或抽取任务，先做好提示、上下文和输出校验。

如果任务有明确的步骤和状态约束，比如审核、订单处理，我会用工作流控制执行路径。如果下一步需要根据探索结果决定，比如调研和故障排查，再考虑自主 Agent。

它们也可以组合使用。固定流程负责必须遵守的业务规则，Agent 在允许的范围里决定怎么找信息、怎么生成方案。

**追问：工作流是完全固定、完全确定的吗？**

工作流可以有条件分支和循环，确定的是允许的状态转换和调度规则。节点里用了模型，生成结果仍然可能有随机性。所以工作流同样需要校验输入和输出。

> **项目补充｜说明选型取舍**
> 这里可以讲【项目名】为什么采用【单次调用／工作流／Agent／混合方案】。准备一个被放弃的方案和具体原因，例如流程已经清楚、额外轮数成本过高，或预设分支无法覆盖实际异常。

### 8. 航班订票客服应该用工作流还是自主 Agent？如何混合？

如果由我设计，我会把需求沟通和航班比较交给 Agent，把身份校验、价格确认、支付和出票放在受控的业务流程里。

比如用户说“下周去上海，尽量便宜”，Agent 可以澄清日期和转机偏好，比较不同方案。选定方案后，程序需要重新核对旅客信息、实时价格、库存和授权，再按供应商协议完成锁座、支付和出票。

交易过程中的异常也要由明确的规则处理。例如支付超时，先查询结果，避免直接重试造成重复扣款；支付成功但出票失败，则进入查询、补偿或人工处理流程。

这样可以保留沟通和探索的灵活性，同时让交易状态始终可检查。具体先锁座还是先支付，要遵循实际业务协议。

> **项目补充｜可结合传统订单、支付项目**
> 如果做过【订单／支付项目】，可以说明你熟悉的状态机、幂等和补偿机制，再补充“如果引入 Agent，我会让它参与【需求理解／方案推荐】，交易约束继续由【现有服务】执行”。不必把已有后端项目描述成已经上线的 Agent 项目。

## 三、工具、上下文与运行效率

### 9. 什么是 ACI？怎样设计模型不容易误用的工具？

ACI 是面向 Agent 的工具接口设计。我会重点考虑模型能不能判断什么时候用这个工具、参数应该怎么填，以及调用后会发生什么。

首先是职责和命名清楚，例如把查询订单和执行退款拆开。其次是参数语义明确，金额用元还是分、时间是什么时区、资源 ID 从哪里获得，都应该说明。返回结果也要包含状态、错误原因和必要的后续查询方式，方便模型继续决策。

对于写操作，我还会考虑权限、幂等和影响范围。用户身份由服务端绑定，不能让模型传一个用户 ID 就获得对应权限。

像数据分析这样的探索任务，可以提供受限的代码执行能力；退款、支付等操作，我会优先提供业务语义清楚、范围受控的专用接口。

**追问：参数符合 JSON Schema 就可以执行了吗？**

还需要检查实际取值和授权。格式合法，只能说明请求在结构上符合要求，不能证明金额合理、资源属于当前用户，或者这个操作已被允许。

> **项目补充｜拿一个工具的修改前后对比**
> 这里可以讲【工具名】原来哪里容易误用，比如金额单位含糊、查询与写入混在一起、错误结果无法判断。再讲你改了【接口或校验】，用什么样本确认问题减少了。最好准备一组真实参数和返回值。

### 10. 受限动作空间在什么场景下优于开放动作空间？

当业务范围明确、错误代价比较高时，我更倾向于限制动作空间。例如退款客服只需要查订单、计算可退金额、申请退款和转人工，没有必要给它任意 SQL 或系统命令执行能力。

这样更容易控制权限、覆盖测试和审计操作。代价是灵活性会下降，遇到没覆盖的情况，需要扩展接口或交给人工。

对于代码开发和探索性分析，操作很难提前穷举，可以提供更通用的工具，但要限制可访问的数据、运行环境和资源预算。

我还会看工具实际能做什么。即使工具列表里只有一个“执行代码”，它的权限也可能很大；限制工具数量并不等于限制了实际能力。

> **项目补充｜讲清允许和禁止的操作**
> 可以结合【客服／内部运营／运维项目】，列出必须开放的动作、被限制的动作，以及超出范围后的处理方式。重点解释限制来自什么业务风险，而不是只说“做了白名单”。

### 11. Agent 的上下文包含什么？是否越长越好？

上下文是模型当前做决策时能看到的信息，通常包括系统指令、工具定义、用户请求、历史交互、检索资料和工具返回结果。

我更关注这些信息是否与当前任务相关、是否可靠，以及有没有反映最新状态。把所有材料都放进去，会增加成本，也可能让关键约束被噪声淹没。

因此我会让稳定规则保持清晰，对文档和工具细节按需加载；执行过程中保留目标、已完成步骤、失败原因和关键证据。长日志或大表格可以存到外部，先返回摘要和定位信息，需要时再读取原文。

对于网页或外部文档，还要标明来源，避免把其中的文字当成系统指令。长期记忆也需要在检索或加载后，才能影响当前这次调用。

> **项目补充｜结合知识库或长任务**
> 这里适合讲【知识库问答／长文处理／多步任务】中一次信息不足或上下文过长的问题。准备：需要保留什么、可以省略什么、怎样找回原始证据，以及如何确认压缩后没有影响回答质量。

### 12. 为什么 ReAct 累计缓存读取量会近似二次增长？怎么降低？

原因是历史会不断增长，而后面的请求又会反复带上前面的内容。假设每轮新增的信息差不多，那么第二轮要读取第一轮的历史，第三轮要读取前两轮的历史，累计起来就是一个等差数列。

缓存可以减少重复计算或降低计费，但已经命中的历史仍可能被后续请求重复计入读取量。所以我会同时优化三个因素：减少不必要的调用轮数，减少每轮返回的无关信息，以及控制送进模型的活跃历史长度。

比如独立查询可以合并或并行，大段日志只返回关键部分，长任务在阶段结束时整理状态，把可回查的材料放在外部。压缩后要检查任务效果，特别是不能把用户约束和失败原因压掉。

**追问：能简单推导一下吗？**

如果初始上下文长度是 `P`，每轮平均新增 `d`，不压缩地运行 `n` 轮，累计输入量大致是：

```text
P + (P + d) + … + [P + (n - 1)d]
= nP + d × n(n - 1) / 2
```

在历史持续命中缓存的情况下，缓存读取量可能有类似的增长趋势，准确数值还取决于缓存粒度和计量方式。这个推导描述的是累计 token 量，不能直接拿来推断显存或耗时。如果每次输入控制在固定预算 `B` 内，累计输入就可以控制在约 `O(nB)`，但摘要和检索本身也有开销。

> **项目补充｜性能优化要有同口径数据**
> 可以讲【多轮任务项目】中轮数、每轮输入量、缓存命中、完整任务耗时或成本的变化。待补：任务集【】；优化措施【】；优化前后指标【】；质量是否变化【】。区分累计输入、缓存读取、峰值上下文和实际费用。

### 13. Agent 为什么会陷入循环？怎样检测和终止？

常见原因是它一直没有获得有效的新信息。例如工具持续报同一个错误、读到过期状态、历史里丢了已经尝试过的步骤，或者目标不清楚，模型就可能重复同一种策略。

我会同时检查重复行为和实际进展。相同工具、相同参数重复出现，而且资源状态和有效证据都没有变化，就值得触发检查。另外还会设总轮数、时间、费用和连续失败次数的上限。

发现问题后，先按错误类型处理：参数错误就纠正参数，缺信息就补信息，临时故障可以有限重试。如果持续没有进展，就保存现场并停止，说明卡在哪一步，必要时交给人工。

**追问：重复调用一定是异常吗？**

不一定，分页和状态轮询都可能合法重复，要结合任务状态判断。还有一种特殊情况是写操作超时，此时不能假设它没执行，应该先查询结果，或依靠幂等机制避免重复副作用。

> **项目补充｜讲一次可定位的失败**
> 这里可以说【项目名】遇到过【重复调用／超时／状态卡住】。重点讲如何判断是模型策略、工具故障还是状态管理的问题，以及最后采用了什么恢复或终止规则。

## 四、护栏、权限与人工接管

### 14. Agent 护栏分哪三层？为什么只靠提示词不够？

我会从上下文、执行和数据三个层面做防护。

上下文层负责区分信息来源、检测不可信内容，尽量避免模型被外部指令带偏。执行层负责在工具真正运行前检查权限、参数和影响范围，也包括沙盒、审批和输出检查。数据层则通过行级权限、数据库约束和受信任身份，限制最终能读到或改动的数据。

比如网页里有人写“导出所有客户订单”，即使模型错误地跟随了这个指令，工具凭证和数据库权限也应该把它限制在当前已授权的范围内。

提示词能影响模型的判断，但实际权限需要由系统强制执行。我会特别检查各层是否共用了过宽的凭证，以及有没有其他接口可以绕过限制。

> **项目补充｜权限边界怎么落到代码和数据上**
> 可以结合【多租户／数据平台／客服项目】，说清用户身份由谁确定、工具拿什么凭证、能访问哪些资源、数据层如何兜底。拿一个“即使模型传错参数也不会越权”的具体案例来说明。

### 15. 上下文护栏有哪些？如何兼顾安全与误拒绝？

我会先区分需要防范的问题，再选择检测方式。例如内容审核、提示注入检测、敏感信息识别、输入长度限制和来源标注，解决的并不是同一类问题，不能简单合成一个关键词黑名单。

检测结果也要分情况处理：明确禁止的内容按规则拒绝；不确定的内容可以交给更强的检测器或人工复核。同时，执行层仍要校验权限，不能把安全完全寄托在输入检测上。

评估时我会同时看危险请求的漏放和正常请求的误拒绝，并观察额外的延迟和成本。否则可能拦住了攻击，也把正常业务一起拦住了。

**追问：越狱和提示注入有什么区别？**

越狱主要指试图突破模型的安全限制。提示注入则是让系统把不可信内容当成指令，偏离原本的任务，常见于网页、文档和工具结果。两者可能重叠，但提示注入也可能只是诱导一次越权读取，并不需要让模型生成有害内容。

**追问：能不能用读取内部激活的轻量探针？**

需要具备对应模型的内部访问和部署条件。普通应用调用黑盒 API 时通常没有这个能力，我会先用实际可用的规则或分类器，再评估检测质量和成本。

> **项目补充｜准备一个漏放和一个误拒绝案例**
> 如果实际做过【审核／风控／Agent 防护】，可以说明某条规则为什么误伤正常请求，以及调整规则后怎样确认没有放开危险请求。只有方案、没有落地时，就用设计假设来讲。

### 16. 同一个工具随参数不同，风险不同，如何动态评估？

我会针对这一次具体操作评估风险，综合看调用者、目标资源、参数、影响范围和可恢复性。工具名称本身只能提供一个基础判断。

比如删除文件，删一个临时文件和删生产配置，虽然调用的是同一个工具，后果差别很大。我会先确认路径实际指向哪里，处理路径越界和符号链接，再检查资源是否在授权范围内、会影响多少文件，以及是否可以恢复。

随后由策略决定直接执行、要求确认还是拒绝。需要确认的操作，要把审批绑定到具体资源和参数，执行时再核对一次，避免确认后目标发生变化。

模型可以辅助理解操作意图，但资源权限和硬性业务限制应该由程序判断，不能只根据模型给出的“低风险”评分放行。

> **项目补充｜同一接口的不同风险**
> 可以讲【批量删除／退款／消息发送／配置发布】接口。准备两组风险不同的参数，并说明系统如何判断权限、限制影响范围，以及如何防止审批内容和实际执行不一致。

### 17. 需要人工确认，但用户不在线、回复慢或含糊，怎么办？

我会把任务保存为等待确认的状态，记录已完成步骤、准备执行的操作，以及还需要用户决定什么。等待超时不能当成同意。

在等待期间，已获授权、能独立推进的低风险步骤可以继续做；需要确认的操作先暂停。同时设置有效期，到期后按业务约定取消、继续保留或转人工队列。

提问要具体，例如确认哪个航班和总金额，避免只问“是否继续”。如果回复仍然不能确定关键参数，就继续澄清。

用户之后回来确认，也要重新检查价格、库存、权限等状态。如果这些条件变了，原来的确认可能已经不适用。对于用户事先明确授权的自动处理规则，则可以在约定范围内执行。

> **项目补充｜长任务或审批恢复**
> 这里可以结合【审批／异步任务／订单项目】，说明等待状态保存在哪里、如何恢复、何时过期，以及恢复时需要重新校验哪些条件。

## 五、模型进步、系统进化与设计模式

### 18. 模型越来越会调用工具，Harness 还有什么价值？

模型越擅长决策，原来一些固定的规划和提示改写步骤就可以简化。但工具执行、权限、业务状态和异常恢复仍然需要系统来提供。

比如模型可以准确决定调用退款接口，但它不能自行决定当前用户有没有权限，也不能只凭生成的文字判断退款是否到账。这些都要结合真实业务状态验证。

而且模型能够执行更长、更复杂的任务以后，状态管理、预算控制、断点恢复和审计会变得更重要。

所以我会把 Harness 的价值放在可靠执行上，同时通过评估持续删掉已经不需要的适配逻辑。模型能力变强，应该让系统有机会更简单，而不是保留所有旧机制再不断加层。

> **项目补充｜区分能力提升与工程保障**
> 如果做过【模型升级／Agent 改造】，可以讲哪些提示或编排步骤被简化了，哪些权限、验证和恢复机制仍然保留，以及做这个取舍的依据。

### 19. 哪些 Agent 工程手段可能随着模型进步而过时？

我会优先看那些专门弥补旧模型短板的代码。比如为了稳定生成 JSON 做了很多字符串修补，或者为了让模型按步骤完成任务，堆了很长的提示和固定规划链。

如果新模型和接口已经能更稳定地完成这些事，就可以评估是否删掉对应逻辑。类似地，生图工具已经能理解自然语言后，原来专门把需求改成标签式提示的步骤，可能也能简化。

不过要区分格式问题和业务问题。结构化输出减少了格式错误，仍然要检查金额、资源归属和操作权限。能力改善也可能来自约束解码或平台接口，不一定全是模型参数的变化。

删除之前，我会比较有无这层机制的任务成功率、成本和回归情况，保留版本和回滚路径。是否保留 few-shot 示例，也应该按实际收益判断。

### 20. Agent 在执行中“学会了”，是否意味着模型参数更新了？

不一定，我会先看改变发生在哪里。

第一种是上下文里的适应。比如模型看到一次工具报错，下一次换了参数，这次会话的表现改善了，但模型参数没有变化。

第二种是保存了外部知识或规则。比如把经验写进记忆、知识库、Skill 或工具代码，下次再加载使用。这能跨任务保留经验，也不需要修改模型参数。

第三种才是通过微调或强化学习等训练更新参数。它更适合需要持续改变模型能力或行为、而且有足够数据和评估条件的情况。

如果只是退款规则变了，我会优先更新可审计的业务规则或知识库。这样更新和回滚都比较直接，不必把每次业务变化都变成一次模型训练。

> **项目补充｜说清经验保存在哪一层**
> 可以结合【用户记忆／知识库更新／模型微调项目】，说明保存了什么、什么时候加载、如何处理过期内容，以及实际有没有更新模型参数。

### 21. 你会采用哪些 Agent 设计模式？分别解决什么问题？

我比较关注五种做法，具体是否引入，要看任务复杂度和失败原因。

第一是把产出和审核分开。审核者根据任务要求和实际结果判断，减少沿着产出方思路继续出错的情况。

第二是按需加载信息。先让 Agent 知道有哪些资料和工具，需要时再读取细节，避免上下文过大。

第三是用追加记录保存过程。重要事件保留下来，方便审计和恢复；送进模型的活跃上下文则可以压缩，不必一直带着所有历史。

第四是改动时同时验证两类样本：这次应该修好的问题，以及原来已经做对、不应该被影响的任务。

第五是让改动尽量小、能够回滚。这样发现问题时更容易定位原因，也方便恢复到稳定版本。

**追问：让另一个模型审核，就能保证正确吗？**

不能保证。审核者也可能有相同的知识盲区，所以要给它清楚的标准和可信证据。关键业务还要结合测试、程序校验或真实状态查询。如果独立审核没有带来足够收益，也没必要为此增加一个 Agent。

> **项目补充｜选一个真正解决过的问题**
> 不需要给五种模式各编一个案例。挑【项目名】实际采用的一种，说清原来的失败、采取的措施和付出的代价，例如多了一次审核调用，换来了什么可验证的收益。

### 22. 如何证明一次 Agent 改动确实变好了？

我会先定义任务完成的标准和主要失败类型，再用同一组有代表性的任务比较改动前后。指标上除了成功率，还要看完整任务的耗时、成本、异常恢复、人工接管，以及危险请求漏放和正常请求误拒绝。

样本也要分开准备。一部分覆盖这次要修的问题，另一部分检查原来正常的能力有没有退化；还要留出没有反复用于调参的独立测试集。

对于结果波动比较大的任务，我会在一致的环境、权限和预算下多次运行，观察平均表现和波动范围。改动也尽量小一些，方便判断收益到底来自模型、上下文还是工具。

**追问：成功率提高，但成本也涨了，算变好吗？**

要结合业务要求判断。如果原来的成功率已经够用，成本上涨可能不值得；如果任务价值高，之前的失败会导致大量人工处理，增加一些模型成本可能合理。我会同时报告成功率、平均任务成本，以及成功任务所对应的总投入，避免只挑好看的指标。

> **项目补充｜最适合展开的评估案例**
> 可以接：“我们在【项目名】里把成功定义为【标准】，用【数量及来源】的任务评估。我负责【改动】，观察到【结果】，同时发现【代价或回归】，最后通过【措施】处理。”百分比要带样本量、统计周期和比较条件。

### 23. Prompt、Context、Harness、Loop、Graph Engineering 有什么区别？

我会把它们理解成工程关注范围的扩展。

Prompt Engineering 主要解决怎么表达指令和示例；Context Engineering 进一步考虑模型该看到哪些信息，以及怎样检索、组织和压缩。

Harness Engineering 关注模型怎样接入工具和真实业务，以及权限、状态、验证和恢复。Loop Engineering 更关注任务如何持续推进、怎样判断进展和结束，以及后续执行如何接续。

Graph Engineering 则把模型循环、程序节点和人工节点组织成执行图，明确依赖、路由和状态如何传递。

这些术语的边界在不同团队里可能有差别。落到项目里，我会先看实际需要：简单循环已经足够，就保持简单；确实有复杂分支、并行依赖或持久化检查点，再引入合适的图编排。

### 24. 用感知、行动、策略三个维度分析一个 AI 产品，并提出改进。

以 IDE 里的编程助手为例。它的感知来自用户需求、读到的代码、项目规范、诊断和测试结果；行动包括搜索、编辑文件、运行命令和测试，具体范围取决于用户给它的权限。

策略上，它会先定位问题，再修改和验证，如果测试失败，就根据错误继续调整。代码任务的路径经常不能提前完全确定，所以这种基于反馈的循环比较合适。

如果由我改进，我会优先让它获取相关规范、调用关系和测试入口；修改时控制范围、保留用户已有改动；完成后用测试和验收条件确认结果。对发布、凭证访问等操作，再设置单独的权限检查。

我也会关注它什么时候停止。测试没跑通、只是耗尽预算时，要留下清楚的状态和失败原因，方便继续处理。

> **项目补充｜结合实际使用经历**
> 可以讲“我使用【工具】完成【任务】，它先做了【操作】，遇到【问题】后调整了【步骤】，我通过【验证方式】检查结果”。
>
> 可以选择实际使用过的编程助手、浏览器 Agent 或调研工具，说明它能看到什么、能执行什么、怎样根据反馈调整。使用产品的经历重点讲观察和验收；参与开发的经历则可以进一步讲接口、状态、权限和评估的实现。
